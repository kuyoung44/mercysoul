# MercySoul Dominion — 30-Day Proof-of-Work Roadmap

**Goal:** turn the public MercySoul identity into a credible, evidence-backed technology presence and create a first usable demonstration.

This roadmap is a plan, not a claim that the milestones have already been completed.

## Phase 1 — Foundation (Days 1–7)
- [ ] Standardize the official MercySoul description across website, GitHub, LinkedIn, Instagram, and Facebook.
- [ ] Upgrade the GitHub profile README in a public profile repository.
- [ ] Maintain a clear engineering portfolio.
- [ ] Link the live site and relevant public repositories.
- [ ] Label capabilities as designed, implemented, tested, or live-verified.

**Deliverable:** a consistent public identity and evidence index.

## Phase 2 — Evidence (Days 8–14)
- [ ] Build a safe, non-destructive MercySoul Vision Brain demonstration.
- [ ] Record a short mobile-friendly screen walkthrough.
- [ ] Demonstrate request → analysis → plan → user review → response.
- [ ] Publish code and reproducible validation instructions.
- [ ] Record test results and link them to a commit.

**Deliverable:** a public demo with clear capability and limitation statements.

## Phase 3 — Visibility (Days 15–21)
- [ ] Publish founder build-in-public updates.
- [ ] Publish selected creative work and AI experiments.
- [ ] Share the founder origin story: building from Oyan, Osun State, Nigeria.
- [ ] Publish a LinkedIn technical update with evidence and links.
- [ ] Keep brand descriptions and links consistent.

**Deliverable:** a documented, consistent public story supported by real artifacts.

## Phase 4 — Opportunity (Days 22–30)
- [ ] Identify relevant AI communities and founder programs.
- [ ] Prepare a short partner/sponsor introduction and project evidence pack.
- [ ] Apply to suitable startup programs when eligibility is verified.
- [ ] Offer AI customer-support and automation services with a clear scope and price.
- [ ] Reach out to prospective first customers respectfully; track responses and outcomes.

**Deliverable:** an outreach pipeline and evidence-backed opportunity list.

## Monthly proof loop
**BUILD → TEST → RECORD → PUBLISH → CONNECT → EARN**

Every public capability should link to a source, test, demo, or deployment record. Do not describe plans as shipped, tests as passing without execution evidence, or deployments as live without verification.

## Approval and safety boundaries
- No approval = no execution for consequential actions.
- Do not make production database changes, migrations, RLS/grant changes, or destructive operations without explicit founder approval.
- Never commit secrets or private credentials.
- Publishing external social posts requires the founder's approval.
- Track dates and status honestly; incomplete work remains unchecked.
